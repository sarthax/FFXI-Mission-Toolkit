Roadmap

Status report and revised roadmap for the Mission Toolkit -- also published as a standalone artifact for sharing outside this app. Started as a proposal for turning the dat-extraction / capture-mining pipeline into something browsable; every phase below is either built and running, on hold, or a newly-scoped future phase with a concrete build-requirements breakdown, not a one-line wish.

Real bugs found this session

  • The Items Obtained tab was showing junk -- two compounding bugs. It pulled every opcode under packet_decode's broad "item_shop" category (full-inventory-sync dumps sent on every zone/login, plus unrelated Synth/Auction/Currency traffic), and opcode 0x020 itself (the one real per-change signal) had a corrupted field definition in packetlyzer_db.xml -- two conflicting field layouts concatenated into one packet block, so item id always read back 0 and quantity read back garbage. Fixed both; validated across 147 real capture zips (264,479+ item-attribute rows, zero decode errors, zero unresolved item ids beyond the expected "empty slot"/gil sentinel).
  • The same corruption pattern affected ~36 other opcodes in the same packet database. 34 fixed this session, each verified against the real LandSandBoat struct and, where real capture data existed, decode-validated. Two remain open (0x00A Zone In, 0x0B4 Config) -- both need a real captured sample to resolve safely rather than a guess.
  • A real capture (Bhaflau Remnants) was silently dropping genuine event data because its eventview folder was nested one level deeper than the ingest pattern expected. Fixed by broadening the pattern; recovered 112 real event rows that were previously silently absent.
  • A capture zip reported as "failed to import" was a genuinely corrupted download, confirmed independently via PowerShell's own Expand-Archive -- the honest per-file error pointed straight at the real cause instead of masking it as a parser bug.
Earlier real bugs (FTS5 corruption, newline-crossing regex, backslash-escaped SQL, the real drop-table foreign key, dark-mode contrast, multi-session capture bundles, and more) are preserved in the full external write-up -- this page focuses on what changed most recently.

Phases

E

LSB-primary core module + Topaz/DSP backport module

Built 2026-09-084 phases, see CORE_AGNOSTIC_DESIGN.md

The toolkit's default target flipped from Topaz-primary to LSB-primary, with Topaz/DSP demoted to an optional backport module rather than a required setup step -- most servers that started on Topaz have since moved to LSB, and LSB is the only actively-developed core. Phase 1 rewrote build_sql_index.py to parse the bundled LandSandBoat checkout instead of a Topaz server (same sql_* table names/shapes every core page already depends on, just a different real source underneath). Phase 2 added a new build_topaz_index.py, structurally parallel to build_dsp_index.py, giving Topaz its own topaz_* tables for the backport module. Phase 3 flipped ID Drift's diff direction (Topaz/DSP vs. LSB as baseline, not the reverse) and gated its nav entry behind a real backport_enabled() check (a real Topaz/DSP checkout present on disk, not just a saved setting string). Phase 4 un-hardcoded setup.bat (LSB fetch now required, Topaz path now optional/skippable) and relabeled the homepage's stat rows. A follow-up pass the same day fixed build_database.py's separate, previously-missed hardcoded Topaz path (items_ours/ keyitems_ours now genuinely read LSB's own item_basic.sql/key_item.lua), added a new topaz_keyitems table so the backport module keeps real keyitem-drift coverage, and fixed two comparison panels (Item Browser's /items/{id} detail page, ID Drift's item/keyitem categories) that had silently started comparing LSB against itself once the primary source changed underneath them.

Future phases (requested 2026-09-06)

Seven new features, not yet started. Each carries a concrete "what this actually requires" breakdown -- real dependencies and real open decisions, not a one-line wish.

6

Video linking, timestamp alignment, transcription

Not startedSchema changeNew external dependency

Associate a capture with a recording of the same session, seek the video to match any event/action/item row, and optionally make the audio searchable.

What this actually requires:
  • A video_path/video_url column on captures -- referenced by path, not uploaded as a blob (real recordings run into GB).
  • Alignment is the real problem, not the seek bar. No field says the video's clock and the capture tool's clock agree. Needs a manual one-time sync: pick one known event, mark where it occurs in the video, compute every other row's offset from that single anchor.
  • Playback UI (an HTML5 <video> with currentTime driven by a row click) is straightforward once alignment exists.
  • Transcription is a materially bigger, separable piece -- needs a real speech-to-text engine (faster-whisper/whisper.cpp) run offline per video, a new timestamped-segment table indexed like dialog_text, and accuracy on in-game audio is genuinely uncertain until tried. Scope as an optional sub-phase after alignment ships.
7

Online hosting and access

Not startedSecurity-sensitiveNo auth exists today

Move the toolkit (or a read-only view) from local-only to something reachable remotely.

What this actually requires:
  • Auth doesn't exist at all today. Every route assumes a trusted local user. Minimum viable is HTTP Basic behind a reverse proxy; a proper login system if more than one person needs distinct access.
  • The destructive routes are the actual risk -- Settings, rebuild, and backup restore/delete need real auth (or exclusion from anything hosted) given this project's own history of a near-miss full-database wipe, guarded against locally with safe_rebuild() and dual-flag confirmation, neither of which assumes a hostile remote user today.
  • Concurrency: SQLite tolerates one writer -- fine locally, needs a real decision (locking/ queueing vs. admin-only writes) once remote.
  • Networking: real domain+TLS for public hosting, or a lighter tunnel (Tailscale/WireGuard) if "online" really means "reachable by a known small group" -- worth deciding which this means before building either.
8

Auto-ingestion from a Windower/Ashita addon

Not startedNew addon (Lua)New capture model

A live capture path feeding this toolkit directly from an in-game addon, instead of capture-then-zip-then-upload.

What this actually requires:
  • Two very different ambition levels. Low-risk: the addon writes the exact same known log formats already parsed, to a watched folder, and a background process auto-calls the existing ingest functions on file change -- no new protocol needed. High-ambition: a true live stream needs a real network endpoint, a "capture that's still growing" concept the current one-shot model doesn't have, and an auto-refreshing UI. Recommend starting with the watched-folder version as its own phase.
  • The addon itself is new Lua work in a different ecosystem than this Python toolkit.
  • Even the low-risk version needs a real decision on when a "session" starts/ends for auto-created captures -- zone change, or a manual in-game command?
9

Workflow for requesting missing capture data

Not startedSchema changeShares a table with Phase 12

A way to flag "this capture is missing X" and track it through to being filled.

What this actually requires:
  • A new entity distinct from a capture -- what's missing, which capture/mission/zone, status (open/fulfilled), who asked and when.
  • Auto-detecting fulfillment is hard; start manual. The honest "closes when a future capture supplies it" version needs Phase 11's checklist logic to exist first -- ship as manually-marked-fulfilled initially.
  • Shares real schema with Phase 12 (flagging bad/missing data) -- worth one capture_annotations-style table (type: request | flag, scope: whole capture | specific row/field, note, status) rather than two systems duplicating the same shape.
10

Capture→server-data export pipeline

Not startedConnects to the paused Phase 5Needs a concrete target schema

A pipeline from a capture to an output format ready for external development into a real private server.

What this actually requires:
  • This is the write-path already scoped and paused as Phase 5, put on hold when it targeted Topaz and no real DSP target existed yet. That target now exists (this session's build_dsp_index.py) -- the real open question is whether this unblocks Phase 5 directly or wants its own separate design, not whether to start from scratch.
  • The transform layer needs to be schema-real: capture_npc_entries → npc_list-shaped rows, real path data → mob_spawn_points-shaped rows, resolved Items Obtained ids → loot-table-shaped rows, each checked against the target codebase's confirmed real column shapes -- the same discipline already used for the ID Drift phase's schema differences.
  • Same review discipline as Phase 5: every generated line cites its real source, output is always a reviewable diff, never an automatic write into a live server checkout.
11

Tag/category-based completeness checklist

Not startedNeeds a hand-authored rule setFeeds Phase 9

Given a capture's tags/content_type, surface what's typically expected and what's actually present.

What this actually requires:
  • "Complete" isn't defined anywhere today. content_type is a free label with no attached expectations -- needs a real, hand-authored rule set (e.g. a real Assault capture should have NPCLogger data, EventView/idview dialogue, and real 0x020 item-attr rows), a domain-knowledge task, not derivable automatically.
  • Implementation shape: a checklist_rules table mapping content_type to expected categories, each backed by a real evaluable predicate (e.g. COUNT(capture_npc_entries) > 0), rendered as a checklist on the capture detail page.
  • Directly feeds Phase 9 -- a missing checklist item is the natural trigger for "request this data."
12

Flag missing or invalid capture data

Not startedShares a table with Phase 9

Let a person mark a specific row, table, or a whole capture as wrong or incomplete -- distinct from the automatic per-file ingest status already built this session, which only reports parse success/failure, not semantic correctness.

What this actually requires:
  • Same capture_annotations-shaped table proposed for Phase 9 -- a flag is the same shape as a request, just a different type.
  • UI: an inline flag control on capture detail rows plus a central open-flags list -- natural to combine with Phase 9's request list.
  • Distinct from, not a replacement for, this session's per-file pass/fail reporting -- that reports "did this file parse," this reports "is this data actually right," which automation fundamentally can't determine for most of what a capture records.
13

Discord integration

Not startedNew external dependencyNeeds server admin consent

Two related capabilities, discussed 2026-09-07: (a) a bot connected directly to the Discord API instead of manually browsing/screen-scraping, and (b) retroactively scanning a channel's real message history to index posted video links (YouTube etc.) and file-host links (Dropbox/Google Drive/Mega) -- catalog only, no downloading.

What this actually requires:
  • A real bot registration and a real permission from someone else. A Discord Application + Bot token from Discord's developer portal (free), then someone with actual admin rights on the target server has to invite the bot with read-message-history permission -- this is the one true gate; nothing else here matters until that happens.
  • History scan is genuinely tractable. A bot (via discord.py or similar) can walk a channel's full history through Discord's own REST API (GET /channels/{id}/messages, paginated) and regex-match message text for known link patterns -- no file downloads, no per-message cost beyond the API call itself.
  • Native Discord attachments are free to size; third-party links are not. A file someone uploaded directly to Discord carries a real size field straight from the API. A Dropbox/Drive/Mega link does not expose real file size in either the raw URL or Discord's own link embed -- getting a real size means a second, separate API integration per hosting service (Dropbox's own API, Google Drive's API), each with its own auth setup. Build link cataloging (URL, channel, poster, timestamp, host type) first since it stands alone; treat real size lookups as a follow-on once it's clear which hosts actually show up in practice.
  • Standard bot-hygiene risks, not unique to this idea: the bot token is a real secret (env var, never committed, rotate if it leaks); request only the permissions actually needed (read history, not manage/kick/ban); a bot needs an always-on host to run reliably (idle on a personal PC only when that PC is on); scanning many/large channels needs to respect Discord's rate limits; and once indexed, the local DB holds other members' message metadata (who posted what, when) -- worth a real retention/visibility decision, not an afterthought, given it's other people's activity, not just the user's own.
  • Naturally connects to Future Phase 8 (auto-ingestion from a Windower/Ashita addon) -- a bot already watching a channel for capture links is the same "watch for new real data, ingest automatically" shape as that phase's low-risk watched-folder version.
