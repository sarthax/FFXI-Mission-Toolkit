Real inventory changes from capture_raw_packets' own 0x020 (GP_SERV_COMMAND_ITEM_ATTR) packets -- separate from key items, since a temp item (e.g. a Nyzul vending-box drink or an Assault temp item) is never a KITrack event, only a real 0x020 packet. This is intentionally narrower than earlier versions of this tab, which also showed every other opcode under packet_decode's broad "item_shop" bucket (full-inventory-sync dumps sent on every zone/login, plus unrelated Synth/Auction/Currency traffic) -- 0x020 alone is the real per-change signal. This packet fires on ANY inventory change (a slot being cleared included, not only gains), so quantity/item can go down as well as up -- read it as "this slot changed", not strictly "obtained". Every row is inherently self-only -- the server telling the capturing client about ITS OWN inventory, no per-packet entity field exists to show (confirmed by decoding real samples). Every row belongs to {% if cap.capturer %}{{ cap.capturer }}{% else %}this capture's (unnamed) capturer{% endif %}.

0x020 also fires on Mog House containers (Mog Safe, Storage, Locker, Satchel, Sack, Case, eight Wardrobes, a second Mog Safe, the Recycle Bin) -- a capturer browsing storage between missions generates just as many rows as anything actually obtained during play (confirmed live: 77% of one real capture's 0x020 rows were non-inventory containers). Even within Inventory/Temp Items, LandSandBoat's own SendInventory() is called only from the client's zone-in handshake and pushes a real 0x020 for EVERY item the character already owns, all at once -- confirmed live as clusters of up to 34 rows sharing the exact same timestamp. "Acquired only" keeps just isolated rows (no other Inventory/Temp Items row at that same instant) -- a real treasure-pool win or reward is never bundled with a dozen others. This is a heuristic (two genuinely distinct events landing in the same rounded second would also get excluded), not a certainty.
