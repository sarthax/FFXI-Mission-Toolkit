How this page works

  1. Start — click New synthetic scenario, or pick a published case and click Fork to copy it.
  2. Describe it — give it an ID and title, say why it exists, and write the Given / When / Then in plain sentences.
  3. Say what to check — pick the observations (what gets looked at) and, optionally, assertions (what each should equal), then link them to a step.
  4. Validate, then Save — Validate checks the draft is well formed. Saving needs the operator token.

Nothing here runs the game or changes any data. A draft is a written test plan that a person reviews later. Given / When / Then are notes for that reviewer; they are not code and are never executed.

Identity and purpose

Given / When / Then — the story in plain words

Write what a tester would set up, do and expect, one short sentence per line. These are notes for the human reviewer. They are not executed and do not drive any check. The actual checks come from observations and assertions further down.

Example: Given “Player has 1 flowerpot in the Mog House” · When “Player plants a seed” · Then “The pot shows a seedling”.

What should be checked? Observations and assertions

Observation = a piece of game state someone will look at while testing. Names starting with client_ are what the game client shows; db_ are what the saved server database holds; gm_ are GM diagnostic read-outs. Comparing client against db is how mismatches get found.

Assertion = one rule about an observation, e.g. “db_bag must be non-empty”. Observations only name what to look at; an assertion says what it should be.

How to build one: (1) pick the observations you need below → (2) optionally add an assertion in the next section → (3) in each step under “Ordered scenario steps”, open Technical provenance… and link the observations and assertions that step uses. Picking an observation does nothing visible by itself; it makes it available to link to a step.

Checks (assertions) — what each observation should be (optional for a first draft)

Click Add check. Each check reads as a sentence: “Check that [what to look at] [must be…] [expected value]”, shown live under the check. Then link it to a step.

Ordered scenario steps

A step is one thing the tester does or checks, in order. Fill in its ID, title and expected outcome. To tie a step to the checks above, open Technical provenance… inside the step and pick its observations and assertions. If you do not know the expected result yet, write UNKNOWN rather than guessing.
