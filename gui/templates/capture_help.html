Raw packet convergence

Raw packet-producing tools feed the common capture_raw_packets evidence store while retaining their own source_format, native source identity, row/block provenance, and optional packet metadata. Equivalent packets may be correlated by opcode + direction + exact raw bytes; the original observations are not deleted or merged.

Packet inspection is capture-native. Each raw packet row can be opened in a contextual decoder keyed by capture_id + seq. It uses the same canonical packet definitions as the standalone scratch decoder, but keeps the session timestamp, neighboring packets, packet header metadata, exact source locator, source hash, and cross-source correlations visible. Decoded fields are color-coordinated with their exact raw byte spans; unclaimed and overlapping bytes remain explicit rather than being assigned guessed meanings.

Future live stream rule: a live FFXI producer should write timestamped observations through the same canonical raw-packet ingestion contract and then use this same decoder/correlation UI. It must not create a second live-only decode database. Endpoint role/direction, decryption state, and inferred semantics stay explicit evidence fields; unknown direction must remain unknown unless independently established.

Canonical chat convergence

PacketDB CHATLOG, CapLog chat/system lines, and Windower Logger daily chat files feed capture_chat_observations. The canonical row keeps timestamp, direction when the source provides it, zone ID/name context, text, source format, source-native identity, and exact row/line provenance. The older capture_caplog_chat table remains for compatibility.

Visual / OCR evidence

Capturebar has no persisted log file, so support is video/screenshot based rather than file ingestion. YouTube OCR includes a built-in capturebar_overlay layout template and capturebar parsing profile for the default Wiggo32 HUD format: zone number/name, target/player name, X/Z/Y coordinates, rotation, main/sub job and levels, moon percentage, and moon phase. Parsed frames materialize as CAPTUREBAR_CONTEXT video evidence with the original frame/timestamp/crop provenance. Custom Capturebar display strings may require a saved layout and/or future parser extension.

Historical tool archaeology

The current archaeology pass audited stock Windower Logger/QuestLog/Pricer, classic and modern PacketViewer families, current Captain PacketLogger/PacketBridge/EventView v2, and Ashita entity utilities. The important distinction is whether a tool actually leaves reusable evidence on disk. QuestLog, old Pricer, and ScanZone do not; Captain PacketLogger is already format-compatible with the PacketViewer/VieweD raw-log family; PacketBridge is a live UDP forwarding opportunity rather than a file format. The detailed inventory and evidence notes are maintained in docs/workbench/CAPTURE_TOOL_ARCHAEOLOGY.md.

Network planes

FFXI capture evidence spans separate network planes. The lobby/character-service TCP flow handles login setup, character/world lists and character selection; the separate search/cache TCP flow handles confirmed player search, party/linkshell lists, search comments, and auction-house listing/history; the world/map flow uses UDP and contains the familiar FFXI packet chunks used by PacketViewer-style tools. Modern private-server loaders may expose additional auth/data/profile sockets that are implementation-specific and should not be treated as retail protocol facts. The detailed research map is maintained in docs/workbench/LOBBY_WORLD_STREAM_RESEARCH.md.

TCP reconstruction

PCAP/PCAPNG ingestion now reconstructs generic bidirectional TCP flows before any FFXI protocol classification. Endpoints are labeled deterministically as A/B rather than guessed as client/server. Reassembled byte ranges preserve TCP sequence boundaries, contributing frame numbers, exact source provenance, and explicit gap/retransmission/overlap/conflicting-overlap diagnostics. Missing bytes are never synthesized. When overlapping segments disagree, the first observed byte is retained and the conflict is recorded for review. Protocol family remains unknown_tcp until a later structural classifier proves lobby, search/cache, loader-auth, or another protocol.

Validated lobby decoding

Reconstructed TCP ranges are now structurally tested for the retail FFXI lobby protocol. A flow is classified as ffxi_lobby only when at least one complete packet has the declared size fully present, the IXFF terminator, a known lobby command, a command-compatible packet size/layout, and a valid MD5 identifier computed with the 16-byte identifier field zeroed. Ports are not used as proof. Known request/response direction can assign endpoint roles only when all validated messages agree; conflicts remain explicit.

Validated lobby messages are stored separately in capture_network_messages with raw packet bytes, command/name, reconstructed sequence span, contributing frames, MD5 status, and decoded non-secret fields. Current decoding includes ResponseKey feature/expansion metadata (including Wardrobes 3-8 flags), ResponseNextLogin world/map and search/cache endpoints, character/world list basics, common character-selection/create/delete/rename identifiers, errors, and client version/expansion fields from RequestLobbyLogin. Authentication/password material is retained only inside the original raw evidence and is not promoted into decoded fields.

PCAP/PCAPNG limits

PCAP support is deliberately evidence-first. FFXI zone traffic uses UDP, but live wire payloads can require session-aware Blowfish decryption and zlib decompression before the familiar four-byte FFXI chunks exist. The adapter therefore always preserves network frames and transport payloads, but it does not guess keys, decompression state, client/server role, or packet direction. Opaque/encrypted datagrams remain network-frame evidence. A UDP payload is promoted into capture_raw_packets only when the entire payload is already a structurally valid stream of known FFXI chunks; promoted rows use direction unknown until independent evidence establishes endpoint roles.

How unsupported files are handled

Files that do not match a supported parser are reported as unrecognized. Known formats found in unexpected paths are content-sniffed and reported as likely known formats so path/layout regressions can be distinguished from genuinely new logger families. Source manifests, hashes, ingestion lineage, and row locators preserve what was actually consumed.

  2. Add the search/cache TCP Blowfish/MD5 session decoder on top of the generic TCP flow layer; lobby classification/decoding is now supported.
  3. Optional preservation of PacketDB ZONES/PACKET_DEFINITION as historical reference metadata.
