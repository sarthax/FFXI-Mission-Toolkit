Feature Trace vs. Behavior Inspector

ToolPrimary questionImportant boundary
Feature TraceWhere is this implemented and how is it connected across server, client, capture, research, validation, and package evidence?Provider-native links are evidence navigation. Ambiguous identities fail closed and generated links do not become synthetic canonical truth.
Behavior InspectorWhat does this Lua-backed actor/controller do according to source evidence?It is static source analysis, not a Lua runtime simulator. Unsupported order, helper behavior, or dynamic predicates remain unknown/raw evidence.

A common workflow is Feature Trace / Entity Dossier → Behavior Inspector → Technical Graph when needed → back to Feature Trace for client/runtime/validation/dependency context.

Feature Trace provider-native wiring

Feature Trace can follow deterministic source-native relationships without writing canonical graph edges. Current server-side examples include item-detail → base item, spawn → group, group → pool, instance entity → instance/entity records, pet → pool, Blue Magic wiring, wiki claim alignments, and the recovered mob-drop chain:

spawn → group → pool / drop rows → item

mob_droplist has no stable upstream primary key, so the Workbench uses the complete source row as a read-only catalog identity instead of inventing a persistent ID.

Behavior Inspector Plain Behavior

Plain Behavior is the default view and uses one backend-generated projection contract:

Trigger → Requirements → Actions / Events → Results / State Changes

Internal rule/helper plumbing is collapsed, but guards, state, resolved helper evidence, targets, source locations, and exact technical node identity remain available. Timer/queue/listener callbacks own their downstream behavior separately so delayed actions are not incorrectly shown as synchronous parent-hook results.

Feature Testing & Validation

Scenario authoring product NOT ACCEPTED / execution BLOCKED. The merged Scenario Developer offers design-only draft controls, not a complete create → publish → scenario catalog → RUN → results workflow. Previous 11/11 isolated browser-control checks did not establish end-user usability. See product gap #1406.

Start here: Feature Catalog lists Toolkit capabilities, not runnable test cases. Feature Testing — Catalog tab is a separate read-only view of existing published scenario definitions; new draft publication into that catalog is unavailable. Scenario Developer is for non-executable drafts. Validation Runs shows separately recorded historical outcomes and evidence; a draft is not a run.

Design-only editing (not a runnable test): Open Scenario Developer; use Guided fields for purpose, behavior and assertions, or Advanced to edit canonical JSON. Inspect local warnings, then Validate for canonical checks. A synthetic design-only operator token is required for guarded draft Save; this token does not authorize Headless, game control or publishing. Reopening an existing saved draft uses expected revision / compare-and-swap (CAS); a conflicting save must be reviewed rather than overwritten. Unsaved-change navigation protections cover some browser events, but native beforeunload dialog appearance and back/forward cache recovery were not confirmed.

Known limitations: Validation errors appear in a summary, and each invalid field is linked to its own message. Forking a published case that lacks steps, or applying Advanced JSON with a wrong-typed field such as cleanup, is rejected with a field-specific message instead of crashing (#1403, fixed). Avoid treating failed UI transitions as saved drafts. There is no generally available draft-to-catalog Publish action, no arbitrary scenario RUN action, no Headless-backed run status/cancel, and no automatic results import. See the Validation area only for evidence already recorded, never as proof this draft executed.

Offline evidence reconciliation: The #1399 backend primitive compares synthetic/in-memory receipt evidence and fails closed on unsupported input. It has no hosted UI route or button, durable persistence, live importer, or authoritative game PASS verdict; it is not part of the end-user authoring workflow.

Use run history and the exact run inspector to review imported observations and failed assertions. Read-only Supervisor investigation can surface candidate source paths when the authorized results database and credentials are configured; it does not execute tests or establish causation.

Key Items: mappings and evidence

Open Key Items, select a client identity, then compare active DSP and reference LSB/Topaz mappings. The Lua dependencies panel filters requires, grants and removes under a selected source lineage. Recorded evidence and Feature Trace / Wiki handoffs are research references, not proof of a live server transition.

Wiki provenance and exact-source navigation

In Wiki, browse cached source-qualified pages and inspect original document, section and locator metadata where imported. From Feature Trace, follow the Wiki evidence path to the exact source ID and page ID. Duplicate headings may be ambiguous and are not auto-selected. Wiki evidence remains reference-only until independently supported by DSP, client or capture observations.

Validation runs and targets

Use Validation Runs to inspect recorded outcomes and evidence, or Live Target Validation to review explicitly configured target checks. A plan, route or source-backed expectation is not a passing execution. Confirm target identity, recorded run context and evidence before treating a result as validated.

Binary Inspector and protocol evidence

Open Binary Inspector with an authorized client binary. Review PE sections, imports, exports, indexed strings, and pattern matches as source evidence. Feature probe sets and protocol compatibility views can compare hypotheses across versions; a heuristic pattern match is not a verified client behavior.

Use the binary comparison view to examine differences between artifacts. The running-client scan requires suitable local access and should be treated as a separate observation, not assumed from a downloaded binary.

Retail Version Explorer

Open Retail Version Explorer to browse known manifests and versioned files, plan a selective download, inspect the downloaded artifact catalog, and compare version metadata. Review a plan before fetching files; existing-file overwrite and file-integrity restrictions still apply. An artifact's PE metadata or version match does not prove the running client uses it.

Client assets and dialog research

Use the Client Overview, Model Viewer, DAT Inspector and Dialog Drift tools to inspect indexed client assets and compare representation changes. Verify the selected client version and provenance of imported files before linking findings to server behavior. Static views, animation/model previews and dialog diffs are research evidence, not runtime acceptance.

Capture browsing, search and paths

Open Captures to select an imported session, review its source and timestamp, and browse the available packet, event and entity views. Use Capture Search or the Query view to narrow specific fields instead of interpreting all captured traffic as one behavior. Path visualizations are projections of recorded observations, not complete routes or verified server state.

Capture ingestion, formats and metadata

Use Capture Import for a single supported package, Bulk Capture Ingestion for bounded batches, and Metadata Import for associated descriptions. Check Capture Format Support before import. Inspect errors, origin and decoding limitations; incomplete captures must not be labelled complete.

Capture review and zone evidence

Use Capture Review to triage observations and their evidence, then open the zone-oriented review where supported. Keep source/run identity and conflicts visible. Captured events demonstrate what was observed in a session; they do not establish generic gameplay rules or independently validate a proposed server implementation.

Video OCR and evidence alignment

Use Video OCR to inspect extracted on-screen text and timestamp alignment alongside capture events. Review ambiguous OCR strings and timing offsets before linking dialogue or UI text to packets. OCR output remains fallible observational evidence.

Migration identity and ID drift

Open ID Drift to compare source and target identifier mappings before preparing any backport. Inspect collisions and unknown mappings as review findings; do not assume identical numeric IDs refer to the same entity across server forks.

Lua, SQL and binding conversion

Use Lua Converter, SQL Converter or Binding Converter to inspect source-to-target adaptations. Review unsupported constructs, symbol resolutions and emitted diffs before accepting a conversion. Source conversion is not an approved deployment or successful runtime validation.

Migration packages, scope and review

Open Packages to inspect migration artifacts and their provenance. Use package creation and scope review to define candidate files and relationships, then Package Review to inspect collisions, approvals and proposed changes. Keep package generation, review and any separately authorized apply stage distinct; a reviewed plan does not write to a server.

Research sessions and evidence

Use Research Sessions to scope an investigation, gather source-qualified evidence and inspect citations before recording conclusions. In Research Evidence, check the originating source and the evidence links; observations and inferred relationships are not interchangeable. A missing link may indicate incomplete indexing rather than absent functionality.

Research gaps and contradictions

Open Research Gaps to identify unresolved questions and missing evidence. Use Research Contradictions to compare conflicting assertions, versions and sources. Keep contradictions open when the source versions, runtime context or identities differ; do not manufacture a single definitive verdict from incomplete records.

Feature Checker and LLM research

Use Feature Checker to inspect evidence requirements and implementation coverage for a selected feature. LLM Research can help navigate retrieved source material, but suggestions and summaries require source verification. Neither a coverage score nor a model response is independent gameplay validation.

Live Client bridge and observations

Open Live Client Bridge to inspect client connectivity, selected source and observation status. Configure the authorized Ashita addon or headless observation source separately. Check source identity, timestamps and connection freshness before trusting a live projection; a connected bridge does not prove complete capture coverage.

Observed entities and movement

In the Live Client console, inspect nearby observed entities and position updates. Distinguish observed client broadcasts from DSP spawn records; entity name, identity and timing may not align across sources. Movement paths reflect sampled observations and can be incomplete between polling intervals.

Live 3D map and zone viewer

Use the Live Client 3D/zone viewer to inspect observed positions alongside mapped server entities, keeping source colors and zone identity in view. Missing positions can indicate visibility or capture gaps, not missing spawns. Viewer navigation and overlays do not validate server behavior or execute client commands.

Server entity lookup

Use Entity Lookup to inspect server-side entity identities, placements and related data. Confirm the active DSP database/profile and zone before comparing results with live client observations. A database row is configured state, not proof that an entity spawned in a recorded session.

Server SQL browsing

Open SQL Browser to inspect selected schema tables and source rows. Use narrowly scoped queries and distinguish loaded database values from reference SQL scripts or migrations. Read-only inspection does not authorize database changes or establish runtime behavior.

Server dialog and event references

Use Dialog Browser to locate dialog references and Event Browser to examine event identifiers and associated source context. Correlate IDs with zone, NPC and script lineage before drawing conclusions. An indexed reference may be unused, version-specific or unreachable without further capture/runtime evidence.

Settings and server administration

Use the Settings page to review selected paths, profiles and configuration before changing active data sources. In Synth & Crafting, inspect recipes and related server data while keeping reference calculations distinct from observed synthesis outcomes. Confirm any action's permissions and preview before executing it.

Items and item editing

Use Item Browser to inspect item records, Item Health to identify incomplete or suspicious mappings, and Item Editor to review proposed item changes. Confirm item identities and active schema before edits; a preview or database value is not evidence of live gameplay correctness.

Missions and progression domains

Use Missions, Assault Tracker, Nyzul Isle, Domains Overview and Shift Master to inspect progression definitions, dependencies and recorded issues. Check selected source lineage and zone/instance identity. Backport status, readiness indicators and source presence do not prove runtime completion.

Zones and spatial editing

Use Zones to inspect loaded zone data and Zone Editor to compare geometry, spawn positions and other mapped entities. Distinguish imported server positions from live observed client positions; a visual overlay or proposed edit is not a gameplay acceptance result.

Validation history and live targets

Use Validation Runs to inspect recorded run outcomes and evidence, and Live Target Validation to examine explicitly configured target checks. Check execution context, timestamps and expected assertions before interpreting results. A configured target or unexecuted plan is not a passing validation.

How the evidence fits together

ConceptMeaning
Catalog / indexed objectA source says the object exists. Catalog discovery does not invent a dependency relationship.
Provider-native relationshipA deterministic relationship encoded by the source schema or indexed evidence. Feature Trace may navigate it without converting it into a canonical graph edge.
Canonical relationshipA recorded evidence-backed relationship such as REQUIRES, REFERENCES, BINDS, USES_ID, or VALIDATED_BY.
Runtime observationA capture observed an entity, packet, event, state transition, or other runtime fact. Repeated observations are evidence, not thousands of new semantic dependencies.
Behavior projectionA source-evidenced readable projection of the technical behavior graph. It simplifies presentation without deleting the underlying Technical Graph.
Dependency closureA recursive view of supported prerequisites or access/obtainability relationships, including AND/OR gates where represented.
ValidationExpected-versus-observed evidence and results. A disagreement remains visible rather than being silently resolved.
PackageA proposed migration unit. A feature and a package are related concepts, but they are not the same thing.

Common workflows

Trace a feature or entity

Open Feature Trace and search by a known name, numeric ID, or canonical ID. Select the correct match when a name is ambiguous. Use focused modes to answer implementation, trigger, effect, dependency, mission, runtime, identity, or diagnosis questions. Follow provider-native links for source wiring and canonical relationships for recorded graph truth.

Understand an NPC/mob/controller behavior

Open Behavior Inspector. Start in Plain Behavior for the source-proven flow. Use Technical Graph when you need exact callback ownership, guards, state edges, helper resolution, source spans, or raw API evidence. Return to Feature Trace for cross-source implementation or runtime context.

Investigate an ID mismatch during a backport

Start with ID Drift, then verify the object in SQL or Entity Lookup. Follow source-specific evidence instead of assuming DSP, Topaz, Topaz-Next, and LSB share a schema or ID layout.

Compare expected behavior with a capture

Open the relevant capture and use its timeline/packet/entity evidence, then review Validation or Feature Trace. Capture evidence tells you what happened in that session; it does not automatically describe every valid game state.

Inspect client-side support

Start at Client Overview. Use DAT and model tools for assets/data and Binary Inspector for EXE/DLL evidence. Keep the client build/snapshot in view when comparing results across versions.

Prepare a migration package

Use Packages after tracing the feature and its dependency scope. Review scope and readiness before applying changes. Legacy Backport Package tooling remains available but is labeled as legacy in the navigation.

Read a Japanese wiki page and translate it

Open Wiki and pick a WikiWikiJP page. Highlight client terms brackets every official game term (auto-translate phrases, item names); hover for the English, or press Show terms in English to swap them inline. Translate to English (machine) translates the whole page with your local Ollama model (choose it in the Model dropdown; first use is slower while the model loads). Translations are drafts: game-specific names can be wrong, so confirm them against Client terms.

Look up a game term in English and Japanese

Wiki → Client terms. Type English, Japanese or kana; each result shows both languages, category and type, and Search JP Wiki finds pages using that Japanese term. Needs data/ja_en_text.db.

Data & indexes

The Home / Project page's Data & Tools section shows which local sources are populated and provides the supported rebuild/install controls. Rebuild an index after its underlying server/client source changes. A zero or missing index can mean “not configured/not built,” not “the game data does not exist.”

Source paths and environment configuration live in Settings. The context bar at the top of the GUI reports the project/source/target/client context the Workbench can actually establish; UNKNOWN is intentionally different from guessing a snapshot or build identity.

Useful navigation rules

  • Follow links instead of re-searching. IDs and objects cross-link into their dedicated views where a safe route exists.
  • Use Feature Trace for breadth; Behavior Inspector and specialized pages for depth.
  • Keep provenance visible. Server forks, client builds, captures, reference sources, and research evidence can disagree.
  • Do not convert missing evidence into absence. Missing provider links, unsupported Lua idioms, or unknown packet fields stay unresolved until evidence proves more.
  • Editors and mutation actions are marked. Read-only investigation should remain distinguishable from actions that create or modify migration/editor state.

For the detailed Behavior/Feature Trace evidence model, see docs/workbench/BEHAVIOR_FEATURE_TRACE_GUIDE.md. For implementation status and planned work, see the Roadmap.

Tracing GUI actions to backend behavior

The Feature Catalog's Documentation accuracy triage → Operator workflow bindings lists selected source-reviewed actions. Select the capability, check the literal GUI control, HTTP method and route, named handler and any delegated helper, and read its safety boundary before acting.

Feature Trace: searching issues a read-only graph query; runtime observation loading separately requests a bounded capture-evidence page. Missing observations do not confirm a path never executes. Wiki: source-qualified article links are read-only, scraping queues an import job, and snapshot export builds a compressed download rather than changing DSP state. Live Client: opening the bridge console and polling entity status are different from saving local headless-observation settings; the latter is a guarded same-origin write, not in-game movement. Captures: events and packets use distinct indexed search modes, while opening the review queue does not resolve exceptions.

When a workflow does not produce the expected result

Open the Catalog's Operator workflow bindings → reviewed paths for the exact control. Read the trigger, known handler signal and recommended next check. A disabled source, invalid request, asynchronous job, and a valid search returning zero indexed matches must not be treated as equivalent.

Trace: import the canonical graph before retrying a missing-graph route; narrow ambiguous searches to a canonical node ID. Wiki: verify source and page ID before accepting evidence; treat scrape receipts as pending until job status/cache health confirms completion. Live Client: correct feed fields and local file permissions and use the authorized loopback browser; a null telemetry snapshot is not an offline-client verdict. Captures: add mode-specific filters, verify ingest/indexing, and clear queue filters before asserting nothing exists.

Selected failure conditions are exercised by isolated offline FastAPI tests using synthetic data, in-memory SQLite, and stubbed receiver/job boundaries; other conditions remain source-only. These tests do not boot the complete Toolkit host, exercise browser JavaScript, run Wiki jobs, or validate a real client/server. Local acceptance is required before updating validation status.
