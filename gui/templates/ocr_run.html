Packetlogger / overlay sections: these text overlays can scroll a lot faster than chat, so 2-5 fps is likely too slow and will drop lines entirely -- a dropped line can't be recovered by OCR or dedupe after the fact. Try a short (10-20s) capture at a high fps first (10-15+) and check the extracted frames/OCR output before committing to a full-length run, since higher fps directly multiplies frame count, disk usage, and OCR time. The "packetlogger" profile parses the real EView overlay/log shape (<< [0x036] GP_SERV_COMMAND_TALKNUM header line followed by Key: value field lines) into a direction, opcode, packet name, and a field key/value table -- modeled on this toolkit's own proven CapLog EView parser. It only extracts what's literally on screen: it does NOT look up what an opcode/field means. Confirmed against a real packetlogger capture (2026-09-27): the overlay panel shows packet history, so one frame often has two or more stacked headers -- each is now split into its own row instead of getting merged into one. Most frames in a real clip still have no overlay content at all (idle background) and will show up as low-confidence noise rows below; use the Conf column to spot the real signal, and Correction to hand-fix anything OCR still gets wrong.
