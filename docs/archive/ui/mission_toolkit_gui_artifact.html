Mission Toolkit GUI

Started as a proposal for turning the dat-extraction / capture-mining pipeline into something browsable. Phases 1–4, capture ingestion across seven real capture-tool log formats, a coordinate-aligned zone-geometry/pathing layer, a real cross-source drift-detection layer, self-serve capture creation, and a real 3D zone viewer are all running code — seventeen-plus pages at localhost:8420, backed by a dozen-plus CLI tools that also still work standalone, over a consolidated ffxi_zone_database.db. This revision folds in a real fourth ID-drift source (old-DSP, alongside client/Topaz/LSB), a folder-upload path for Captures with honest per-file pass/fail reporting instead of one opaque bundle result, a real data-integrity bug found and fixed in the Items Obtained tab (traced to a corrupted opcode definition and an overbroad packet category — see the new bugs list below), a 34-opcode audit of that same packet-decoder database against real LandSandBoat source, and seven newly-scoped future phases (video linking, hosted access, live addon ingestion, a missing-data request workflow, a capture→server-data export pipeline, tag-based completeness checklists, and manual data-flagging) with a concrete build-requirements breakdown for each.

Real bugs found building it, not hypothetical ones

  • External-content FTS5 corruption. A missing delete trigger let a --force re-run silently corrupt the dialog search index — switched to a standalone FTS5 table with explicit deletes instead.
  • Newline-crossing regex. Python's \s matches newlines, so a comment-matching regex was bridging a bare NAME = NUM, line into an unrelated comment on the next line — misattributed real drift findings until caught.
  • Backslash-escaped quotes in raw SQL. 'Gigas\'s Bats' broke a hand-rolled tokenizer that only handled SQL-standard '' escaping — found via a real schema-drift warning, not assumed.
  • pos_rot holding non-integer values despite the column being declared tinyint in the real schema — a strict int() cast crashed the SQL indexer on real data.
  • Module-level sys.stdout wrapping in every CLI tool broke on import once gui_server.py tried to reuse them as libraries — moved under each tool's own __main__ guard.
  • A Starlette version bump changed TemplateResponse's signature (request became a required first positional argument, not part of the context dict) — six call sites silently rendering as 500s until traced.
  • Case-mismatch dropdown state. Zone names stored uppercase in the DB vs. mixed-case in some URLs meant a picked zone didn't show as selected on reload — cosmetic, but a real UX bug, not just data.
  • Wiki reverse-lookup could only find pages that link to an entity, never the entity's own article. A canonical page rarely wikilinks to its own title, so "Jaggedy-Eared Jack" surfaced only an incidental hunts-listing page and never its real article — found live by the user spot-checking a lookup. Fixed with a second index (wiki_pages, 47,328 real page titles) checked first, labeled canonical page vs. mentions it rather than merged into one undifferentiated list.
  • A different private server's custom content was silently mixed into wiki results. BG Wiki hosts CatsEyeXI's own private-server documentation alongside retail content, under a real, filterable category — 10,854 reference rows and an unknown number of page matches were contaminated before the user caught it. Excluded at ingestion in all three consumers (wiki_lookup.py, wiki_compile.py, build_wiki_index.py), not filtered per-query.
  • The real drop-table foreign key is mob_groups.dropid, not mob_pools.poolid. Confirmed directly against Topaz's own C++ (mobutils.cpp's InstantiateAlly query), not assumed from the schema shape — a pool has no drop table of its own, every spawned group can carry its own dropid.
  • Dark-mode form controls had a background color but no explicit text color, so inputs and selects fell back to the browser's default black-on-white widget rendering against a dark surface — unreadable. Fixed with explicit token colors plus color-scheme for native dropdown/scrollbar chrome CSS alone can't reliably style.
  • The decorative in-game minimap has no known, verified per-zone pixel scale/offset — overlaying a real path on it would have meant guessing that alignment and presenting it as correct. Solved differently: rasterize the client's own collision mesh (real world-space geometry, the same space captures report x/y/z in) top-down instead, via a new xi-tinkerer-py binding onto xi-tinkerer's own AGPLv3-licensed Wavefront-OBJ exporter. The x/z axis-sign convention was verified empirically, not assumed: real capture points averaged 1.33 units from the nearest mesh vertex under (x, -z), versus 15–33 units off under the other three sign combinations. See Zone geometry + pathing below.
  • sql_mob_pools.cmbDelay was being parsed and then silently thrown away. build_sql_index.py's column list already named it, but the actual INSERT tuple never included it -- a real dormant bug, found only once AttackDelay ingestion needed something to cross-check against. Fixed with the same explicit-migration pattern used for dropid earlier.
  • A capture-observed key item id can't be trusted to match key_items.keyitem_id -- because that's exactly the field known to drift. KITrack/EventView cross-references had to join by real display name, not either source's id, or the join would silently return nothing for any item already flagged drifted by the readiness check (confirmed live: "map of Ilrusi Atoll" is id 2763 in key_items, but the real client-observed id from a live KITrack capture is 1869).
  • Multi-session capture bundles are a real, different shape from everything ingested before. Blitzkrieg.zip, Defuse the Threat.zip, and azure_experiments.zip each turned out to hold 11–14 independently-named subfolders (real mechanic-testing sessions like "win bluethunder spawn testing 3"), each a complete capture with no shared manifest. Ingesting the zip as one bundle would have silently merged 36 real sessions' entities into 3 fictitious combined captures -- caught before ingesting, not after, by checking bundle structure first. ingest_batch() (new ingest-batch CLI command) treats each subfolder as its own capture instead.
  • FastAPI silently ignores a POST body field with no Form(...) annotation. The 3D viewer's "Build it now" button posted a return_to field meant to bounce the user back to the exact page they were on after a zone mesh finished building -- it kept landing on the homepage instead, because a plain str = "/" default only binds to a query parameter, never a form-encoded body field, with no error raised either way. Fixed by declaring it Form("/"); caught live by the user reporting the redirect looked wrong, not by inspection.
  • The 3D multi-entity zone switcher plotted the newly selected zone's paths onto the OLD zone's mesh. /zones/{zoneid}/view3d_all's zone-picker dropdown only resubmitted zone_db as a query param -- the mesh file loaded ({zoneid}.obj) stayed pinned to whatever zoneid the URL's path segment happened to have on first load, since nothing recomputed it from the newly picked zone. Switching from Caedarva Mire to Periqia kept rendering Caedarva Mire's real geometry with Periqia's real path data drawn over it -- silently wrong, not an error. Found live by the user noticing the mesh didn't change. Fixed by resolving the real zoneid from zone_db server-side and 303-redirecting to the matching URL whenever they disagree, so the address bar and the rendered mesh can never drift apart again.
  • The Items Obtained tab was showing junk — two compounding real bugs, not one. First, it pulled every opcode packet_decode.categorize_opcode() buckets under its broad item_shop category: full-inventory-sync dumps sent on every zone/login (Inventory Count/Finish/List — thousands of rows per capture) plus entirely unrelated traffic (Synth Result, Auction House, Currencies). Second, and more fundamentally, opcode 0x020 (the one real per-change signal, GP_SERV_COMMAND_ITEM_ATTR) had a corrupted definition in Packetlyzer/packetlyzer_db.xml: two conflicting field layouts concatenated into one packet block, so item_id always read back 0 and quantity read back garbage like 4294901760. Fixed both — narrowed the tab to real 0x020 rows only, resolved item names live against items_ours/items_external, and repaired the XML field layout, verified against LandSandBoat's real 0x020_item_attr.h struct. Validated at scale: bulk-ingesting 147 real Assault/Salvage zips (225 captures, 264,479+ item-attribute rows) produced zero decode errors and zero unresolved item ids beyond the expected "empty slot"/gil sentinel values.
  • The same corruption pattern (two conflicting field layouts concatenated into one packet block) turned out to affect ~36 other opcodes in the same packet-decoder database, not just 0x020 — found via a systematic duplicate-field-name scan across the whole XML. 34 were fixed this session, each individually verified against the matching real LandSandBoat struct under src/map/packets/{s2c,c2s}/*.h and, where real capture data existed, decode-validated (turning up genuinely satisfying real data: a player named "Tacocat" with a literal bazaar message reading "tacocat spelled backwards is tacocat.", and clean real per-Assault-zone point totals in the currencies packet). Two remain open — 0x00A (Zone In) has three conflicting fragments across a very large struct where this session's own offset recomputation disagreed with the existing XML by a consistent +4 bytes with no real sample to arbitrate, and 0x0B4 (Config) has real trailing fields missing from the XML entirely, not just mislabeled — both need a real captured sample of that exact opcode to resolve safely, which the user plans to gather later rather than have either guessed.
  • A real capture (Bhaflau Remnants) was silently dropping genuine event data because its eventview folder was nested one level deeper than the ingest pattern expected (eventview/<capturer>/simple/<zone>.log instead of the capturer-less eventview/simple/<zone>.log the pattern required) — the same real per-capturer nesting quirk already handled for NPCLogger, just missed for EventView. Fixed by broadening the pattern to match an optional capturer folder; recovered 112 real dialogue/CSID event rows that were previously silently absent, with zero visible error.
  • A capture zip reported as "failed to import" turned out to be a genuinely corrupted download, not an ingest-pipeline bug — confirmed independently via PowerShell's own Expand-Archive ("End of Central Directory record could not be found"), so the honest per-file error message pointed straight at the real cause instead of masking it as a parser problem.
Direction change mid-build: the user decided to stop patching Topaz's inherited dialog-id drift (it's a client-generation mismatch versus DSP/Darkstar's original target, not really a Topaz-authored bug — see topaz_dsp_pivot_strategy) and instead focus remaining Assault work toward eventually backporting to a real DSP server. That directly affects which parts of the roadmap below still make sense — see the callout in Phase 5.

02What's actually slow

Four concrete frictions, all hit this session, all fixable by the same underlying change: index once, browse and query after.

Every search re-scans the ROM

--scan parses all ~47,000 .DAT files fresh, every time, taking ~2.5 minutes — and a single matching string can hit a dozen files, most of them wrong-language or wrong-client-version duplicates.

No side-by-side against what's wired

Confirming a real dialog id means opening the JSON dump in one window and IDs.lua in another, then eyeballing the diff by hand — the exact off-by-one and off-by-six bugs found this session went unnoticed for weeks because nothing surfaces the mismatch automatically.

Six tools, six output formats

YAML, JSON, CSV, a SQLite DB, static Markdown, raw stdout — cross-referencing "is this captured entity in instance_entities.sql yet?" means opening several of these in sequence and holding the join in your head.

No spatial context

Real positions exist (FFXI‑DATS, mob_spawn_points) but there's no map to look at — deciding which of 20 unwired spawn points belongs to which mission is done by comparing raw x/y/z coordinates by eye.

03Shape of the tool

Not a rewrite of any existing tool — a browser-based front end that calls them. Everything below is additive: the CLI scripts keep working exactly as they do today, for anyone who wants to script against them.

Core workflow it should support

  1. Pick a zone. See every real dialog-table entry, searchable, with the current IDs.lua value shown alongside — drift highlighted automatically, the way this session found it by hand five separate times.
  2. Pick an NPC or mob — by id or by name — and get one page: every real fact this specific Topaz install actually knows about it, pulled live from its own SQL and Lua, not a snapshot.
  3. Pick a CSID. See the decompiled pseudocode with the real dialog text substituted in for every message-id reference, not the numeric id alone.
  4. Search across every zone at once for a text fragment, backed by an index built once — not a 2.5-minute rescan per query.

Two local roots, not one

The setup this session actually needed both: a real FFXI client (C:\ValhallaXI\...) for dat/dialog ground truth, and the Topaz server checkout (C:\topaz) for SQL/Lua. The GUI's config is just those two paths — everything in Phase 1 only needs the client root; everything from Phase 2 on needs the server root too. Point it at a Topaz checkout with no client installed and dialog lookups simply go quiet; point it at a client with no server checkout and the NPC-profile page shows dat/capture facts with an empty "in this server" column. Neither root is required for the other's features to work.

Scope note. The write path — generating instance_entities.sql rows or IDs.lua blocks from a GUI selection — is real value, but it's Phase 4 on purpose. Everything before it is read-only, which means it's safe to build and use immediately without any risk to the live SQL/Lua the server actually runs on.

04Phased roadmap

Original timeline estimates removed below where the phase actually shipped — replaced with what got built. The plan itself held up well; the estimates didn't need to matter once this was worked in short, real sessions instead of scheduled weeks.

Static client index

✅ Built — Dialog Search, Browse by Tag pages Read-only

Scoped wider than just dialog tables on a second look — POLUtils' own MassExtractor and xi-model-viewer both already solve pieces of this that are worth reusing outright rather than re-deriving.

Real find, verified against our own client, not just documentation. POLUtils' own MassExtractor source locates zone files by direct arithmetic, not a lookup table: dialog table file id is 6420 + zoneid (zones 0–255) or 85590 + (zoneid−255) (256–511); mob list is 6720 + zoneid; every global string category (key-items.xml, missions-assault.xml, etc.) has its own fixed real id. Tested directly: 6420+77=6497 resolves to Nyzul Isle's real table (7692 entries, matching exactly); 6420+50=6470 resolves to the exact Whitegate file this session already confirmed by text. This replaces slow scanning and ROMFileMappings.xml's incomplete category list with an instant, direct lookup — and along the way surfaced that Whitegate has a real second dialog table (fixed id 57945, 15,845 entries), later confirmed this session to actually hold both MAZWEEN_SHOP_DIALOG's and SALUHWA_SHOP_DIALOG's real ids once the search was widened to the first table too. Formula first, dat-extractor --resolve to confirm against the actual installed client second — the same file-id space can carry real per-build gaps (the mob-list2 base id didn't resolve against our client at all).
  • Dialog tables — resolved by formula first, dat-extractor's parser reads them as a library call, into one FTS-indexed SQLite table, searchable across every zone at once. Every zone gets checked for a second table the way Whitegate has one, not just the first hit.
  • NPC lists, straight from the client. Same formula (6720 + zoneid) locates the file; xi-model-viewer's parseNpcList() reads it — fixed 32-byte records, Shift-JIS name + real server id, ~15 lines of code, no capture needed. A ground-truth source this pipeline doesn't currently use at all.
  • Type confirmation as a safety net. xi-model-viewer's sniffZoneDat() identifies dialog/events/npclist purely from a DAT's byte structure — run after the formula resolves a candidate, to confirm it's really that type before trusting it (belt-and-suspenders, given real per-build gaps exist).
  • Global reference tables already extracted. POLUtils' MassExtractor_output has real, structured (not free text) global tables sitting on disk right now, at the exact real file ids the formula table above confirms — a master mob-list (name↔id, not zone-scoped), key-items.xml and per-category items-*.xml (name, plural, real description per entry), and missions-*.xml / quests-*.xml with the full real client text per mission/quest — area, objective, recruitment requirements, giver NPC, summary. Ingest these as their own indexed tables rather than re-running MassExtractor; they're more authoritative than a wiki page for Phase 4 since they're straight from the client, not a fan transcription.
  • A second, independent extractor for cross-checking. XiyanFlowC/FFXIDat is a separately-written DAT/DMsg/event-string parser with its own SQLite/CSV export, not a fork of POLUtils' lineage. Wire it in as a second opinion, not a replacement: run it against the same file and diff its output against dat-extractor's. This is the same discipline as the four-way item-id check in the provenance section below — two independently-written parsers agreeing on a value is real signal, and them disagreeing flags a parsing bug worth chasing down before either is trusted for that entry.
  • A parser for IDs.lua's text{} block (it's a flat Lua table literal — regex-tractable) shows the currently-wired value next to the real one, flags any mismatch red
  • Don't reinvent the write-back — port it. LandSandBoat/UpdateExtractor already exists to do exactly this half of the job: it consumes a POLUtils MassExtractor dump and writes directly into a server checkout's zones/<zone>/IDs.lua, with real, working logic for text-id extraction, formatting, and ordering. That's the same task audit_dialog_drift.py and this session's own hand audits (Nyzul's 55-id fix, Whitegate's ~50-id pass) have been doing manually. Its own TODO list is explicit about what it does not yet handle — SQL items/mob-spawn/NPC-list updates, and mob/NPC id shifts specifically — so it would not, on its own, have caught the offset-class bugs found this session; it's a real head start on the mechanical write-back, not a replacement for the drift-detection logic itself. It also targets LSB's own checkout layout, not Topaz's, so the realistic path is porting its extraction/formatting approach rather than running it unmodified against C:\topaz.

Zone/file browser replicating POLUtils' current view sits on top of all of it — but browsing was never the actual gap. The gap was that POLUtils only lets you look at one category in one zone at a time; this makes all of it one searchable, cross-referenced index.

Builds on: dat-extractor, audit_dialog_drift.py's existing comparison logic, xi-model-viewer's sniffZoneDat()/parseNpcList(), POLUtils' existing MassExtractor_output, XiyanFlowC/FFXIDat as a second extractor, LandSandBoat/UpdateExtractor's IDs.lua write-back approach (ported, not run as-is), and the real file-id formulas found in scragg0x/POLUtils (a fork with genuine unique commits, the only one of 39 forks that had any).

Topaz architecture cross-reference

✅ Built — Entity Lookup, SQL Index, Zero-Position/Unregistered pages Read-only Needs the server root

This is the "everything about NPC X" page. Two indexers, both static analysis over the existing Topaz checkout — nothing about the source files changes, nothing needs annotating:

  • SQL indexer. Walks every .sql file under C:\topaz\sql once, parses every INSERT INTO table VALUES (...) (a genuinely regular format across this codebase — every table this session touched fit it), and keys each row by its first column. Querying an id then means one indexed lookup across every table instead of six manual greps.
  • Lua indexer. Walks every .lua file under C:\topaz\scripts, resolving two address forms at once: a raw numeric id (GetNPCByID(17093430, ...)) and a named constant traced back through that zone's own IDs.lua (ID.npc.VENDING_BOX). Topaz resolves an NPC's actual behavior script by its npc_list.name column, not its numeric id, so the indexer also matches that name against scripts/zones/<Zone>/npcs/<Name>.lua directly — the same lookup done by hand every time a script needed identifying this session.

One id or name in, one page out: real name and position (dat ground truth, if the client root is configured), every SQL row across npc_list / mob_spawn_points / mob_groups / mob_pools / instance_entities / instance_list, every Lua file that touches it (the npc/mob script itself, any instance object that spawns or references it, any mixin it uses), and whether a capture has ever actually observed it.

A live source, not just static ones — retail reconciliation

Everything above cross-references data that already exists on disk: dats, SQL, prior captures. That misses the case where retail itself has since changed, or where no capture of a given zone/NPC has ever surfaced. Content readiness compiler

✅ Built — Wiki Compiler page Read-only Not Assault-specific
What actually shipped vs. what was proposed. Link-walking, name resolution against Topaz's real tables, and the ✅/🟡/🔴 status pill all shipped close to the original shape. Two real gaps found live and fixed along the way: a wiki page's own {{Item Tooltip|Name}} template markup carries entity names too, not just [[wikilinks]] (missed "Siren's Tear" until caught); and a canonical article rarely wikilinks to itself, so the reverse entity→wiki lookup needed its own page-title index, not just the link-graph one (see the Jaggedy-Eared Jack bug above). missions-*.xml/quests-*.xml as a stronger primary source ahead of the wiki was not built — the compiler still goes to wiki_lookup.py first.

Feed it a source — a BG Wiki page (via wiki_lookup.py's existing offline dump), or pasted text — for a mission, a BCNM, a quest, anything. It comes back with every real fact Phase 2/3 can find about the things that source mentions, and an honest list of what it can't find at all.

Why this is tractable, not just aspirational

The temptation is free-text NLP over the wiki prose — guessing which words are NPC names. Don't: BG Wiki pages already mark this up explicitly. Every [[NPC Name]] / [[Item Name]] internal link in the dump wiki_lookup.py already reads is a candidate entity, handed to you by the wiki's own markup. Extraction is "walk the page's own links," not pattern-matching prose — the same distinction this whole session drew between trusting a real source and guessing from context.

For missions and quests specifically, Phase 1's newly-indexed missions-*.xml / quests-*.xml (real client text: area, objective, recruitment requirements, giver NPC) is a second, even stronger source — check it before falling back to the wiki page at all. Same extraction shape either way: structured fields in, not prose to parse.

What compiling actually does

  1. Pull every linked NPC/item/key-item name off the page.
  2. Resolve each name against Topaz's own tables (Phase 2's indexer) and, for items/key items, the same name-matching approach id_bridge.py already uses — because raw LSB/retail ids can't be trusted (2,910 of 3,242 key items drifted this session's own finding), matching has to go by name, then confirm the real id.
  3. Cross-check any key item the page implies against keyitems.lua's real enum, and any objective/stage the page describes against whatever enum the target system uses (tpz.nyzul.objective, a BCNM's own win-condition table, etc.) — flagging a described mechanic that has no matching real enum value at all, not just a missing row.
  4. Compile one report: found-and-wired (✅), found-in-SQL-but-no-script (🟡), name not found anywhere in this Topaz install (🔴), and ambiguous — multiple real candidates for one wiki name (❓, needs a human pick, never auto-resolved).
Ambiguity is the normal case, not the exception. Given this session's own key-item drift numbers, expect most non-trivial pages to come back with several 🔴 and ❓ rows. The report has to make that legible at a glance — a status pill per entity, not a wall of text — and it has to carry wiki_lookup.py's own caveat forward explicitly: reference only, verify anything load-bearing, never presented as settled.

Two ways to use the output

  • Manual. The report page itself — work the 🔴/❓ rows by hand, same as this session's own research passes.
  • Handoff packet. One button exports the same report as structured Markdown: the wiki excerpt, every resolved real id with its source table, every gap explicitly labeled as a gap. Built to be pasted straight into an AI coding session as grounding context — which is exactly what happened by hand, repeatedly, this entire session (wiki text in, real ids and gaps established, then scripting). This just automates assembling that packet instead of you typing it fresh each time.

Builds on: Phase 2's SQL/Lua indexer (this is why it isn't Assault-specific — the indexer already covers every table), Phase 1's missions-*.xml/quests-*.xml/key-items.xml/mob-list tables, wiki_lookup.py as fallback, id_bridge.py's name-matching approach, and the provenance layer below for the ✅/🟡/🔴/❓ status itself.

Video linking, timestamp alignment, transcription

Not started Schema change New external dependency

Associate a capture with a recording of the same session, seek the video to match any event/action/item row, and (optionally) make the audio searchable.

What this actually requires.
  • Storage: a video_path/video_url column on captures — referenced by path like a source zip, not uploaded into the DB (real session recordings run into GB, far past what SQLite should hold as a blob).
  • Alignment is the real problem, not the seek bar. This needs a real, hand-authored rule set — e.g. a real Assault-mission capture should have at least one NPCLogger-format source, some real EventView/idview dialogue data, and (per this session's fix) genuine 0x020 item-attr rows — a domain-knowledge task, not something derivable automatically from the data itself.
  • Implementation shape: a checklist_rules table mapping content_type → a list of expected categories, each backed by a real evaluable predicate (e.g. COUNT(capture_npc_entries) > 0), rendered as a ✓/✗ checklist on the capture detail page — structurally similar to the existing per-file ingest-status table, one level up in granularity.
  • Directly informs Phase 9 — a missing checklist item is the natural trigger for "request this data," once both exist.

Flag missing or invalid capture data

Not started Shares a table with Phase 9

Let a person mark a specific row, table, or a whole capture as wrong or incomplete — distinct from the automatic per-file ingest status already built this session, which only reports parse success/failure, not whether the data is semantically correct.

What this actually requires.
  • Same capture_annotations-shaped table proposed for Phase 9 — a flag is the same shape as a request (scope: whole capture | specific row/table/field, a note, a status), just a different type value. Build once, cover both.
  • UI: an inline flag control on capture detail rows (timeline events, items, actions) plus a central open-flags list — the natural place to combine it with Phase 9's request list, since both surface "things a human needs to look at" for a capture.
  • Distinct from, not a replacement for, the per-file pass/fail reporting shipped this session — that reports "did this file parse," this reports "is this data actually right," which automation fundamentally can't determine for most of what a capture records (a real position, a real dialogue line, a real drop) — a human call, by design.

Discord integration

Not started New external dependency Needs server admin consent

Two related capabilities, discussed 2026‑09‑07: (a) a bot connected directly to the Discord API instead of manually browsing/screen-scraping, and (b) retroactively scanning a channel's real message history to index posted video links (YouTube etc.) and file-host links (Dropbox/Google Drive/Mega) — catalog only, no downloading.

What this actually requires.
  • A real bot registration and a real permission from someone else. A Discord Application + Bot token from Discord's developer portal (free), then someone with actual admin rights on the target server has to invite the bot with read-message-history permission — this is the one true gate; nothing else here matters until that happens.
  • History scan is genuinely tractable. A bot (via discord.py or similar) can walk a channel's full history through Discord's own REST API (GET /channels/{id}/messages, paginated) and regex-match message text for known link patterns — no file downloads, no per-message cost beyond the API call itself.
  • Native Discord attachments are free to size; third-party links are not. A file someone uploaded directly to Discord carries a real size field straight from the API. A Dropbox/Drive/Mega link does not expose real file size in either the raw URL or Discord's own link embed — getting a real size means a second, separate API integration per hosting service (Dropbox's own API, Google Drive's API), each with its own auth setup. Build link cataloging (URL, channel, poster, timestamp, host type) first since it stands alone; treat real size lookups as a follow-on once it's clear which hosts actually show up in practice.
  • Standard bot-hygiene risks, not unique to this idea: the bot token is a real secret (env var, never committed, rotate if it leaks); request only the permissions actually needed (read history, not manage/kick/ban); a bot needs an always-on host to run reliably (idle on a personal PC only when that PC is on); scanning many/large channels needs to respect Discord's rate limits; and once indexed, the local DB holds other members' message metadata (who posted what, when) — worth a real retention/visibility decision, not an afterthought, given it's other people's activity, not just the user's own.
  • Naturally connects to Future Phase 8 (auto-ingestion from a Windower/Ashita addon) — a bot already watching a channel for capture links is the same "watch for new real data, ingest automatically" shape as that phase's low-risk watched-folder version.

05Provenance layer: multi-source correlation

✅ Built — real field_sources table, live on every Entity Lookup page

The missing piece underneath every phase above, not a phase of its own. Every value this tool shows — a dialog id, an item name, an NPC position — currently gets presented as if it came from one place. It never actually does. This session alone pulled the same fact from a real client dat, a cached POLUtils extract, a live capture, an LSB SQL row, and a wiki page, and those sources disagreed often enough that "which one do we trust" was itself most of the work.

Make that explicit instead of silent: every field the tool displays carries a source and a confidence, and when two independent sources land on the same value, that agreement is the confidence signal — not a person's gut call.

That's not a bug in the data model — that's the actual finding: the tool should surface exactly that disagreement, by source, instead of quietly picking one value and moving on. A human still makes the call (as happened this session), but the tool's job is making the conflict visible, not resolving it for you.

Four-way agreement as a real confidence signal

The other model's framing of this — client dat, Windower Resources, LSB, wiki all agreeing on an item id as a genuine confidence marker — is sound, and it's the same principle already governing every fabrication rule in this project: never invent an id, always verify by text against a real source, never trust two external sources agreeing without checking against our own client first. This is exactly what entity_profile.py's real field_sources table now does automatically — one row per (entity, field, source), not one row per entity, so agreement between sources is the confidence signal and a disagreement shows both values side by side with a CONFLICT pill instead of one silently overwriting the other.

How this plugs into the phases above

  • Phase 2's SQL/Lua indexer becomes one more source row per id, not a separate system — "does Topaz implement this" sits next to "what does the client say this is" instead of requiring a second lookup elsewhere in the tool.
  • Phase 4's ✅/🟡/🔴/❓ status pill is a provenance summary already — this section just makes explicit that the pill should be clickable, expanding to the actual source list that produced it, the way the SALUHWA_SHOP_DIALOG row above does.

This is a display and storage convention — one extra sources column/table threaded through the schema Phase 1–4 already need — not a new subsystem, and not its own phase with its own timeline. Build it in from the start of Phase 1 rather than retrofitting it later; retrofitting provenance onto data that's already been flattened to a single value means re-running every extractor a second time just to recover what was discarded.

08Open questions

  • How the SQL/Lua indexer actually "integrates." The recommended default is zero-touch: pure static analysis over the checkout as it sits, rebuilt on demand, nothing written back, nothing added to the source tree. The alternative is a generated sidecar — one cache file (SQLite, sitting outside C:\topaz entirely) that persists the parsed index between runs so a cold rebuild isn't needed every session. Both are safe; the sidecar is purely a speed trade, not a change to how the server or its scripts work. Worth deciding now since it shapes Phase 2's storage layer.
  • Index refresh. The full-ROM index only needs rebuilding when the client updates, which is rare; the SQL/Lua index needs rebuilding whenever the Topaz checkout changes, which during active development is often. Is an on-demand "rebuild index" button enough for both, or does the Topaz-side one want a filesystem watcher?
  • Position rendering. resolved Went further than a flat scatter plot, and further than originally scoped — both a coordinate-aligned 2D top-down rasterization and a real 3D/WebGL viewer over the client's actual visual mesh are built, see Zone geometry + pathing above. The user's own live reaction to the 3D viewer once built: the 2D top-down loses real fidelity (passable-terrain silhouette only) that the 3D mesh doesn't — open follow-up is whether the 2D rasterization is worth investing further in (e.g. baking in more collision-mesh detail) or whether it should just defer to the 3D viewer as the primary spatial view going forward.
  • Multi-client-version handling. This session hit a real false-positive from a duplicate dialog table at a different client version — should the index tag every entry with which ROM path it came from, so the GUI can show "3 candidate files, here's why this one's the real one" instead of picking silently?
  • Name-match confidence in Phase 4. Exact-name matches are safe to show as ✅ automatically; near-misses (punctuation, "the" prefixes, pluralization) are exactly where the 90%-drift key-item problem lives. Does a near-match still land as ❓ for a human to confirm, or is there a confidence band worth auto-accepting — and if so, what's the actual bar, given how badly a wrong auto-accept would poison a downstream AI handoff packet?
  • Where Phase 5 stops. Drafting SQL/Lua as a reviewable diff is the safe scope — should it go further and open a local diff view against the actual working tree, or stay at "copy this block into the file yourself"?
  • FFXIDat's actual coverage. Confirmed useful as a second extractor and for its SQLite/CSV export, but its README-level feature list hasn't been checked line-by-line against dat-extractor's — worth a real diff pass before Phase 1 to see how much of its parsing is genuinely redundant versus filling a real gap (its DMsg/event-string path in particular).
  • Provenance storage granularity. Per-field source tracking (the field_sources table above) is cheap for scalar values like a dialog id, but gets larger for something like a full mob spawn row with a dozen columns — worth deciding whether provenance is tracked per-row or per-field before Phase 1's schema is finalized, since that's a much more painful migration to do later than to get right at the start.
  • How close is Topaz's IDs.lua to LSB's, actually. UpdateExtractor's write-back logic assumes LSB's own checkout layout and formatting conventions. This session's own zone audits (Nyzul, Whitegate, Leujaoam Sanctum) all worked against Topaz's IDs.lua shape without ever diffing it directly against a current LSB checkout — worth an actual side-by-side before Phase 5 to know whether porting UpdateExtractor's formatter is a light adaptation or effectively a rewrite.
