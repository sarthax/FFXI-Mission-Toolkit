## 3. Fixture identity and attestation rules

The JSON has three *simulation rows*. **Only two keys come from the actual published canonical catalog**, `moghancement/MOG-09` and `inventory_observation/INV-OBS-01`. The third `fixture_only/SYNTH-CASE-1` is a **fabricated, explicitly isolated v2 thought experiment** used to test independent CASE `synthetic_case_ref` versus exact `SYNTH_STEP_1` `synthetic_step_ref`. It is **NOT** an actual published scenario or allowable runner. Its `SYNTH_STEP_2` deliberately has an empty direct association: neither the case source nor the first step's source may be promoted to that step. All 64-digit `aaaa...`, `bbbb...`, `cccc...` digest fields are artificial syntax placeholders, **not** actual `local_definition_sha256` computed on the real v1/v2 bytes. A later implementation must calculate actual digests from the accepted #1322 canonical serializer, not these strings.

Stable case identity is exactly `(feature_id,case_id)`; the read envelope's `scenario_id` is an alias **of the exact canonical `case_id` value**, not a separate project, editor revision, Headless operation ID, captured step, or stage index. `schema_version=1` even when optional `contract_version=2`. Missing or unsupported revisions fail explicitly; a matching local digest is at most structural read-model agreement, **never signed/deployed source identity or permission to update the catalog**. Provider descriptor IDs like `toolkit.persisted.*` are *not* `required_observation_id` labels; only future independently reviewed exact-key crosswalks `(feature_id,case_id,required_observation_id)` may nominate a candidate provider. No claimed observer `SOURCE_INTEGRATED` or `PR_ONLY` means effective deployed readback/approved oracle.
