**Publication coherence / mandatory optimistic read pin (proposal):** all five reads reference a server-side **immutable, deterministic, versioned** publication snapshot of the canonical published catalog. List response returns `publication_snapshot_id` (opaque public revision identifier, **not** a credential) and each row's `local_definition_sha256`; the subsequent `get/revision/sources/preflight` MUST require both the exact snapshot ID and per-case `expected_sha256`, reject missing/malformed/mismatched values, and read all CASE/STEP/preflight material from the **same pinned snapshot**. The catalog may change between HTTP calls: if pinned revision is unavailable, or a case has changed, return one sanitized typed `BLOCKED/STALE_PUBLICATION` (suggested HTTP 409), **never** silently recompute sources/requirements from a newer snapshot or supply partial mixed-revision data. If implementation cannot retain snapshots, fail closed on any publication change, rather than pretending multiple reads were atomic. `local_definition_sha256` is still **LOCAL_SERIALIZATION_ONLY**, not a signature, deployed source attestation, local editor draft revision or approved oracle. A future owner-reviewed wire-contract revision is required because #1330 currently describes expected digest on `get` only: the new required cross-method pinning is a **change request**, not an implemented or accepted extension.

**Cursor and size failure rules (proposal):** use a **separate server-held HMAC key / versioned key ID** (never bearer-token bytes in cursors) to integrity-protect opaque cursor data containing authorization principal/scope, exact filter tuple (`feature_id`, `runner_class`), `limit`, sorted last-key, immutable `publication_snapshot_id`, expiration and key ID. If tampered, expired, rotated out, changed scope/filter/limit, stale snapshot or invalid UTF-8 => **sanitized typed BLOCKED/CURSOR_INVALID_OR_STALE (suggested HTTP 409)** without page restart or partial results. Server-side query length, cursor length, field multiplicity and maximum response encoding checks are mandatory. The page's `limit <=25` is *not* permission to exceed **65,536 actual UTF-8 bytes**, even if 25 individually valid items fit the item-count bound: if **full encoded page including metadata** would be oversized, return **typed BLOCKED/RESPONSE_BUDGET_EXCEEDED (suggested HTTP 413), with no rows and no next cursor**; caller may retry explicitly with smaller `limit` and a fresh valid snapshot-bound page request. Never silently discard/trim items, advance the cursor over hidden rows, or leak partial data. Per-detail canonical spec <=32,768 encoded bytes and per-source count <=50 are independent additional caps; reject before serializing to client. Bounded sanitized error envelopes must themselves fit the size cap. Test multi-page traversal for stable order and zero skipped/duplicated identities, including publication change between page requests.
