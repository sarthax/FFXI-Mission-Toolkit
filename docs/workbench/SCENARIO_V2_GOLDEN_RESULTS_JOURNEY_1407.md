## 1. First priority: a human can understand results

**Navigation spine, proposed:** **Scenario Suite** → **Run History** → **Run Detail** → **Step Evidence** → **Compare Runs**. Secondary spine, later: **Scenario Test Catalog** → **Scenario Detail & Versions** → **Create/Edit Draft** → **Validate & Publish** → **Preflight** → **Run** → **Results**. A new user's first useful workflow is interpreting recorded evidence, *not* exposing a disabled Run button with no explanation.

Existing routes are **not** the new spine: `/feature-catalog` is the global Toolkit capability catalog; `/feature-testing` (including `?tab=catalog`) is existing feature-testing/catalog context; `/scenario-developer` is design-only draft editing; `/validation/runs` provides existing validation-history context. **Do not claim** any of these publishes a draft to a versioned searchable scenario catalog or launches an arbitrary Headless scenario. ### Dense but readable result layout (desktop and 360px)
Header: **MOG-09 · v1 · run attempt N** / **Evidence UNKNOWN** / **Task COMPLETED** (these words must always be readable independently). Secondary row: run ID, snapshot time, data age, toolkit/headless/server SHAs, environment/character alias (redacted), evidence completeness. Below: left ordered step list with labels and state; right **Given | Action | Expected | Observed | Verdict + Why**, followed by provenance drawer. On narrow width, stack header → step list → selected step details; do not hide UNKNOWN explanation or security warnings behind hover. Color is supplementary; use screen-reader-accessible live status summaries, descriptive links, visible focus, persistent step numbers, meaningful keyboard navigation and non-modal error remediation. Avoid raw JSON in primary experience; advanced trace displays exactly source-authenticated raw evidence with safe redaction. Content density should make a failed/unknown condition obvious without requiring code knowledge.

## 3. Mapping and wire contract boundaries
User-facing game verbs (move, talk, engage, wait, inspect inventory, observe KI/quest/event) map to **one of** (a) syntactically known native XIHeadless `ScenarioActionSchema` actions, (b) Toolkit authorized read-only observation collectors, or (c) unsupported requests. Each step must declare typed field, units/range, source revision/path, identity-resolution status, permission, observation freshness/completeness, approved oracle/comparator, and reason when unsupported. The native `ScenarioExpectationSchema` accepts a limited field vocabulary (zone, hpp, event_active, event_id, position, party metrics); Toolkit R7 inventory/progression readbacks are **not** implicitly native Headless expectations. Source support ≠ runner support ≠ observed evidence ≠ oracle approval ≠ gameplay verdict. Wire/version contract and HEADLESS deployment identity are currently unapproved; no attempt to translate a user pick into executable MCP requests.

## 4. Failure and state semantics for seven fixture classes (#1408)
Ask A's #1408 offline fixtures to supply explicit distinct examples: authoritative PASS with actual comparable oracle (synthetic labeled, never claimed real), contradictory observed FAIL, preflight BLOCKED, insufficient-evidence UNKNOWN, cancellation after accepted task, stale/conflicting revision or attempt, and missing or mismatched source/identity NOT_COMPARABLE. Preserve separate task status and independent verdict in every view; a task completing successfully does not imply test PASS. Always list which evidence and permissions are missing. Client, server, capture and persisted SQL scopes must not silently combine into one "observed".
