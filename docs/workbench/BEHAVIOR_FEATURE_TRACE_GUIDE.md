# Behavior Inspector and Feature Trace — evidence workflow

Status: **current merged behavior/implementation research model**  
Last reconciled: **2026-10-04**

Behavior Inspector and Feature Trace answer different parts of the same investigation.

- **Behavior Inspector** answers: *What does this Lua-backed actor/controller do, according to source evidence?*
- **Feature Trace** answers: *Where is this feature/entity implemented and how is it connected across server, client, capture, validation, research, and package evidence?*

They deliberately share evidence and handoffs, but they do not collapse into one truth model. Behavior Inspector is a source-static behavior projection; Feature Trace is a cross-source identity/relationship navigator.

## Behavior Inspector work completed

The Behavior Inspector finish pass moved the tool from a useful technical graph into a stable admin-facing behavior explanation while preserving the exact evidence underneath it.

### Clarified Flow, Plain Behavior, and Technical Graph

Behavior Inspector now opens on **Clarified Flow**. The three presentation layers are:

1. **Clarified Flow** — the default mission/admin-facing view, including source-proven branch structure, event lifecycle identity, stage → event → next-stage summaries, and verified stage-value continuity where the backend can prove it.
2. **Plain Behavior** — the compact compatibility/admin summary produced by the backend evidence-preserving projection.
3. **Technical Graph** — the complete detailed evidence/debug graph.

Clarified Flow does not infer runtime ordering across hooks. Cross-hook event identity and stage continuity remain explicitly non-causal/`UNPROVEN` unless runtime evidence independently proves ordering.

### One authoritative Plain Behavior contract

Plain Behavior is generated by the backend and attached to the technical behavior payload. The browser renders that contract instead of maintaining a second independent set of collapse/summary semantics.

This removed a major drift risk: the tested Python projection and the browser can no longer silently disagree about what constitutes a trigger, requirement, action, event, result, or state change.

### Human-readable behavior without deleting technical evidence

Plain Behavior groups source evidence as:

**Trigger → Requirements → Actions / Events → Results / State Changes**

Implementation scaffolding such as internal rule nodes, raw helper-call nodes, and nested helper-callee plumbing is collapsed from the plain view. The supporting guards, resolved helper identity, helper inputs/effects, state, targets, source locations, and technical node IDs remain available for drill-down.

The Technical Graph remains the complete extracted evidence graph and is not simplified or rewritten by the Plain View projection.

### Callback ownership and duplicate prevention

Timer, queue, and listener callbacks are treated as real behavioral boundaries.

- the parent hook shows scheduling or listener registration;
- the callback appears as its own trigger flow;
- callback effects belong to that callback flow;
- duplicate callback-body observations are suppressed only in Plain View when their source lines fall inside the proven callback source span;
- the Technical Graph retains the complete observations for audit/debugging.

This prevents the plain summary from presenting delayed/listener behavior as if it happened synchronously in the parent hook.

### Guards, state, events, and helpers

The finished projection recovers incoming guard evidence even when the technical graph represents conditions upstream of internal rule nodes. Literal state transitions and event outcome relationships are promoted only where the source structure proves them.

Shared `xi.<module>.<function>` helpers support exact/ambiguous/unresolved resolution and bounded one-level impact expansion. Dynamic or unsupported helper semantics stay explicit rather than being guessed.

### Closeout boundary

Behavior Inspector is now considered foundationally complete. New Lua idioms or additional deterministic helper semantics are future evidence expansion, not unfinished architecture.

Detailed contract: `docs/workbench/BEHAVIOR_INSPECTOR_CLOSEOUT.md`.

## Feature Trace work completed in this effort

Feature Trace was strengthened from a mostly canonical/hard-coded traversal into a provider-aware implementation navigator that can follow deterministic relationships directly from indexed source records without manufacturing canonical graph edges.

### Provider-native implementation paths

Feature Trace treats provider-native links as read-only navigation evidence. Supported server families include the generic SQL index plus LandSandBoat, Topaz, and DSP catalogs, alongside client identity, captures, research, validation, packages, and reference-wiki evidence.

Provider relationships fail closed when the target cannot be resolved uniquely. Numeric similarity alone is never enough to manufacture identity.

### Deterministic server wiring

The merged provider work includes deterministic navigation for supported schema relationships such as:

- item detail rows → base item;
- spawn → mob group;
- mob group → pool;
- pet → pool;
- Blue Magic wiring → spell / mob skill where supported;
- instance entity → instance;
- instance entity → uniquely matching NPC or mob record;
- reference-wiki claim alignment → page alignment and underlying claims.

The branch reconciliation also recovered an important unmerged drop-chain slice:

**spawn → group → pool / drop rows → item**

`mob_droplist` has no stable upstream primary key, so Feature Trace uses the complete source row as a read-only composite catalog identity rather than inventing a persistent synthetic ID.

### Drop-chain transplant

The old `feature-trace-drop-chain-benchmarks` branch contained useful work but had diverged significantly from newer `main`. It was not merged wholesale.

Instead, the unique capabilities were transplanted onto current `main`:

- explicit `mob_droplist` catalog identities;
- `mob_groups.dropid → mob_droplist` expansion;
- `mob_droplist.itemId → item_basic` expansion;
- drop/item-aware focused trace vocabulary;
- executable scenario benchmark contracts;
- an end-to-end notorious-monster benchmark proving the drop chain.

This preserved all newer provider work already on `main`, including instance/entity, pet/pool, wiki alignment, ambiguity handling, and other fail-closed behavior.

The transplant was merged by PR #474 after Workbench Regression and Src Layout Regression passed.

Branch reconciliation details: `docs/workbench/FEATURE_TRACE_BRANCH_RECONCILIATION_2026-10-04.md`.

### October 4 provider-closure pass

The latest Feature Trace pass closed several previously one-way evidence paths while preserving the same fail-closed identity model:

- reviewed/automatic `MAPPED` reference-wiki mappings can navigate to the exact indexed implementation row only when `target_table + target_key` resolve uniquely;
- captures can navigate to the exact client identity snapshot for their stored `client_build` only when one snapshot has the matching `version`;
- Research sessions can navigate to explicit canonical feature/entity roots;
- Research proposals and Validation results can navigate to an exact canonical subject only when the literal `subject_id` resolves in exactly one canonical namespace;
- Validation runs can navigate to explicit canonical features;
- migrations can navigate to explicit canonical features;
- migration actions can navigate to explicit canonical artifacts.

These are provider/cross-store navigation links, not persisted canonical graph edges. Missing targets, duplicate targets, ambiguous generic subjects, unsafe reference targets, and unresolved mappings produce no link rather than a guessed relationship.

The durable matrix and testing boundary are documented in `docs/workbench/FEATURE_TRACE_CLOSEOUT_2026-10-04.md`.

## Focused Feature Trace modes

Feature Trace modes answer a specific question rather than returning one giant undifferentiated graph. Current modes include implementation, triggers, effects, dependencies, mission progression, runtime evidence, identity, diagnosis, and all evidence.

The implementation/dependency vocabularies recognize item/drop relationships so ordinary mob/NM traces can retain drop-chain evidence rather than filtering it away.

Provider-generated evidence remains separate from canonical graph truth. The UI may display the generated relationship, provenance, target record, and source-native basis without inserting a synthetic canonical edge.

## Executable trace benchmarks

Scenario benchmarks are executable coverage contracts instead of descriptive examples only.

A scenario can require:

- a trace mode;
- a root kind;
- minimum relationship count;
- required relationship concepts;
- required relationship generators.

The NM benchmark constructs a deterministic Topaz-style source dataset and proves that a normal trace can navigate:

**mob spawn → mob group → mob pool + drop rows → dropped items**

It also verifies that the provider-native traversal does **not** create canonical graph edges as a side effect.

## How the two tools work together

A typical entity investigation should flow like this:

1. Start with **Feature Trace** or **Entity Dossier** to establish identity and implementation branches across SQL/server/client/capture/reference evidence.
2. Follow a Lua/script handoff into **Behavior Inspector** when the question becomes “what does this actor/controller do?”
3. Use **Clarified Flow** for the readable source-proven branch/lifecycle view.
4. Use **Plain Behavior** for the compact summary when that is easier to scan.
5. Open **Technical Graph** when exact helper/rule/callback/state evidence is needed.
6. Return to **Feature Trace** for downstream implementation, client identity, runtime/capture, validation, research, package, or dependency context.

The important distinction is:

- Behavior Inspector explains **source-proven behavior**.
- Feature Trace explains **cross-source implementation and evidence relationships**.

Neither tool should convert missing evidence into a claim that gameplay behavior is absent.

## Evidence and safety rules

Both tools follow the same conservative rules:

- preserve source provenance;
- fail closed on ambiguous identities;
- keep runtime observations separate from static source claims;
- do not infer execution order from unrelated hooks;
- do not invent canonical relationships from catalog similarity;
- do not assign gameplay meaning to unsupported packet/source fields;
- retain technical/raw evidence when a simplified interpretation is not justified.
